## 2. 新しいPCで再開する手順

1. **入れる物**
   - Git
   - Node.js 22 以上（手元では 24 を使っていた。GitHub Actions は 22）
   - VS Code と Claude Code（いままでと同じ進め方をするなら）
2. **取ってくる**
   ```
   git clone https://github.com/tghcgu/madori.git 間取り作成
   cd 間取り作成
   git checkout develop
   npm ci
   # Windows は入っている Edge でテストするので、これだけでよい。
   # ほかのOSでは、テスト用のブラウザも入れる: npx playwright install chromium
   ```
3. **動くか確かめる**
   ```
   npm run dev        # http://127.0.0.1:5173/ を開く
   npm test           # 単体テスト（この時点で 197 件すべて成功）
   npm run test:e2e   # 画面のテスト（約5分。PASS: の行が 30 本）
   npm run build
   ```
   取ってきたばかりの環境では、E2E が途中の再読み込み（`page.reload`）で止まって失敗することがまれにある（下の「気をつけること」）。もう一度実行すれば通る。
4. **GitHub に push できるようにする**: GitHub のアカウント（tghcgu）でログインする。`gh auth login` か、Git の認証情報マネージャーを使う。
5. **Claude Code で続ける**: このフォルダを開いて話しかける。`CLAUDE.md` は自動で読まれる。前のPCの Claude のメモ（`~/.claude/projects/.../memory`）はPCの中にしかないが、中身はすべて `CLAUDE.md` とこのファイルに移してある。

### Windows で `npm` が動かないとき

PowerShell の実行ポリシーで `npm.ps1` が止められることがある。`npm.cmd` を使うか、Git Bash から実行する（README の「トラブルシューティング」も参照）。

## 4. 公開の仕組み

- `develop` に push → Cloudflare がプレビューをビルド（数分）
- `main` に push → Cloudflare が本番をビルドし、GitHub Actions が GitHub Pages に公開する
- `vite.config.ts`
  - GitHub Pages 用のビルド（`DEPLOY_TARGET=github`）では、置き場所を `/madori/` にする
  - ビルドしたコミットの番号を `__APP_COMMIT__` としてアプリに入れる。Cloudflare では `CF_PAGES_COMMIT_SHA`、GitHub では `GITHUB_SHA`、手元では `git rev-parse` から取る
- `scripts/plan-edition.mjs`: ビルドした `index.html` を `dist/plan/index.html` にも置く。`index.html` の先頭で場所が `/plan/` なら、`data-edition="plan"` を付けて間取り専用版として動く
- **公開されたかの確かめ方**: `npm run check:deploy -- develop`（または `main`）。公開中の JavaScript に、いまのコミットの番号が出るまで待つ
- 公開されないときに見る所:
  - Cloudflare のダッシュボードにあるビルドのログ
  - GitHub の Actions にある「Deploy to GitHub Pages」の結果（`npm test` が失敗すると止まる）

## 5. いつもの作業の流れ

1. `develop` が `main` と同じかを確かめてから始める（`git fetch` → `git rev-list --left-right --count origin/main...develop`）。
2. `develop` で作る。
   - 使う人に見える変更なら、`src/changelog.ts` に今日の日付で書き、`npm run changelog` を実行する。
   - 説明が変わるなら、README も日本語と英語の両方を直す。
3. テストする。
   - 必ずやる: `npm test`、`npm run test:e2e`、`npm run build`
   - 家具を変えたら: `npm run test:visual` と `npm run compare`
4. コミットして `develop` を push する（コミットメッセージは英語）。
5. `npm run check:deploy -- develop` でプレビューに出たのを確かめる。できれば画面でも操作してみる。
6. ユーザーにプレビューの URL と、変えた所を短く伝えて、「マージ」を待つ。
7. 「マージ」と言われたら、`main` に fast-forward して push する。
   ```
   git checkout main && git merge --ff-only develop && git push origin main && git checkout develop
   ```
8. `npm run check:deploy -- main` で本番2か所を確かめて、伝える。

## 6. 守ること（と、そうなった理由）

| きまり | 理由・経緯 |
| --- | --- |
| 本番の前にプレビューで見せ、「マージ」で本番へ | 2026-10-02、確かめないまま本番に出た変更が続いたとき「まず本番じゃなくて試しで俺に見せてね」と言われた |
| 2Dの記号と、3Dを真上から見た形を必ず同じにする | 2026-09-29、岩の2Dと3Dの形が違っていたとき「2dと3Dがあってないのはぜったいにやめろ」と強く言われた。形のデータは `src/furniture-shapes.ts` で共通にする。3Dが難しいときは、2Dだけのデザイン（`FURNITURE_VARIANTS_2D_ONLY`。3Dは標準の形のまま）にしてもよい |
| 前のデザインは消さずに残す | 「昔の差分も残してほしい」。記号やモデルを作り直すときは、前の物を別デザインとして残す（例: 観葉植物の「らせんの葉」） |
| 2Dの記号に文字を使わない。部屋・床に既定の名前を付けない | 2026-09-25、「冷」「TV」などの文字の記号に「文字は絶対に使うな すぐに戻せ」、既定の名前「部屋 9」に「デフォルトで文字いらない」。見分けは線・形・塗り分け・図柄（冷蔵庫の雪の結晶など）だけで。数字や文字に見える形（小さな楕円2つが「00」に見えるなど）も避ける |
| PL/GM の分け方（GM専用・隠し扉・PL表示・PL/GM別の画像）は入れない | 2026-10-02 のプレビューを見て「PL用GM用とかはいらないかな」。本番に出す前に外した |
| 更新履歴を書く | 2026-10-04「これまでの更新履歴つけろ」。アプリの左の欄と README に、日付ごとに載せる |
| サイトにメールアドレスを載せない | 2026-10-03、前に載せていた連絡用のアドレスを、ユーザーの希望で消した。問い合わせは Google フォームと GitHub Issues だけ |
| 新しい家具やデザインは歓迎 | 「もっと差分とか新しい3D作れ」。増やすときも上の決まり（2D=3D、文字なし）を守る |

### `src/main.ts` の中（`// ---- 見出し ----` で区切ってある。行番号は変わるので、関数名で探す）

- **データ**
  - `PlanState` / `Entity`（部屋・壁・ドア・窓・家具・図形・テキスト）と `state`

- **2Dの描画**
  - `render2d()` → `drawStyledPlan()`（絵柄の切り替え）→ `drawPlan()`
  - `drawPlan()` は、方眼・部屋・ほかの階の透過・ラグとペン・壁・窓・ドア・家具・図形・屋根・テキスト・選択のつまみの順に描く

  - 別デザインは `SYMBOL_VARIANTS`（「2D記号の別デザイン」の見出し）
  - 2Dは全体で1つの `ctx` に描く。オフスクリーン（透かす階・透明度のある色・画像の書き出し・記号の見本）は `ctx` を差し替える
- **操作**
  - `handlePointerDown/Move/Up`（`drag` の状態）、当たり判定は `hitTest()`、キーは `keydown`（R・F・V・L・Delete・Ctrl+Z/Y）

- **選択中の欄**: `updatePropertiesPanel()` が選んだ物に合わせて HTML を作る（人の模型・ペン・足跡・破片はそれぞれの `…EditorHtml` と `bind…`）

### 2Dの絵柄（`src/plan-style.ts`）の仕組み

- **筆・和風**: 描き先（canvas）を包んで、道すじを記録する。
  - 線は筆の形の多角形に作り直す（入り・揺れ・止めや払い・太い線のかすれ。`brushStrokeParts`）。同じ形の線は結果を控えて使い回す。
  - 筆圧の強弱は色合いの `swell`（筆・墨絵は 1、ほかは控えめ）。毛の束の部品ごとに墨の濃さを返し、入りは濃く、かすれる所は薄く塗る。`inkBleed` で線のまわりをにじませる（筆・墨絵だけ）。
  - 塗りは縁を少し波打たせ、和紙になじむ色にする。
  - 最後に和紙の模様を乗算で重ねる。
- **墨絵・古地図・黒板・水彩・クレヨン**: 筆と同じ描き先（`createBrushContext`）で、色合い（`BrushPalette`）だけを替える。
  - 黒板とクレヨンは線がところどころ途切れる（`grain`）。水彩は塗りの縁を濃くし（`washEdge`）、塗りにむらを重ねる（`texture: "bloom"`）。クレヨンは塗りに紙の目を残す（`texture: "tooth"`）。墨絵は床の模様の色を抜く（`patternGray`）。
  - 筆の仲間は、床の模様（木・草など）の上に紙や板の色を薄く重ねる（`patternVeil`。模様の色が浮かないように）。
- **ドット・レトロゲーム**: 画面と同じ細かさで描き、ドットごとに真ん中の1画素の色をとって縮め（GPU）、大きく映す（`drawPixelPlan()`）。
  - 細い線は、描くときにドットのます目に沿った1ドットの線にする。
  - 文字は控えておき、最後にぼかさずに描く。
  - レトロゲームは、縮めたドットを `retroColors()` で緑の4色にする（間の明るさはディザ。並びは間取りに合わせて動かす）。
- **鉛筆**: 線を、少しずつずれた何本かの細い線にする（`sketchLines`）。塗りは色鉛筆の薄い色に、濃さに合わせた斜線を重ねる。
- **マンガ**: 塗りを、色の濃さに合わせた網点のトーンにする（`toneLevel` → `toneTile`）。網点は間取りに貼り付け、45度に傾ける。
- **ポップ**: マンガと同じしくみで、色の網点（`halftoneTile`）と太い黒い線にする（`createPopContext`）。
- **設計図・ネオン・CAD・ホラー・コピー**: 形はそのままで、線・塗り・文字の色だけを置き換える（`createRecolorContext`）。ネオンは線の下に太い半透明の線を引いて光らせる。コピーは床の模様を描いてから色を抜く（`grayPattern`）。
- **入口と表**
  - `main.ts` の `drawWrappedPlan()` が、`styleContext()`（描き先を包む）で描いてから `styleFinish()`（紙の模様・縁の暗がり）を重ねる。ドットとレトロゲームだけは `drawPixelPlan()`（`isDotStyle()`）。
  - 線画（`planStyle`）と背景（`planBackground`、一覧は `PLAN_BACKGROUNDS`）は別々に選ぶ。地の色・方眼・仕上げは `planLook()`（= `lookStyle()`。背景が `auto` なら線画の絵柄）で決め、`StylePass.look` に持たせる。筆の仲間には地の色を `paper` で渡し、床の模様に重ねる色にする。
  - 絵柄ごとの地の色と方眼の色は `STYLE_LOOKS`、書体は `FONT_FAMILIES`、紙の模様は `PAPER_RECIPES`。
  - メニューの見本は、`refreshStyleThumbnails()` が開いているタブの分だけ、`drawStyleThumbnails()` で小さな部屋を描く（線画の見本はいまの背景で、背景の見本はいまの線画で。同じ組み合わせは描き直さない）。
- **絵柄を1つ足すとき**: `PlanStyle`・`PLAN_STYLES`（分類 `group` も）・`STYLE_LOOKS`・`FONT_FAMILIES` に足し、`styleContext()` と（紙の模様があれば）`styleFinish()` に分岐を足す。メニューの見本は自動で増える（見本の説明 `hint` は8文字まで）。`tests/plan-style.test.mjs` の絵柄の一覧と、`tests/editor.mjs` の `looks`（地の色と壁の見え方）にも足す。
- **全部に共通**
  - 選択のつまみなど操作用の印は、`deferOverlay()` であとから絵柄なしで描く。
  - 大きく拡大しても重くならないよう、画面の外は切り落としてから描く。
  - 描き直しは1回あたり、設計図・CAD・コピー・マンガ・ポップ・ネオン・ホラーで2〜5ms、鉛筆で10〜20ms、ドット・筆・墨絵・古地図・黒板・水彩・クレヨンで10〜30ms、レトロゲームで25〜35ms（標準は2〜3ms）。

### データと保存

- 間取りはブラウザの `localStorage` に保存する（キーは `madori-quick-3d-plan`）。
- 見ていた場所・表示の設定・絵柄などは `madori-quick-3d-view-state` ほか、`madori-quick-3d-…` のキーに保存する。
- サーバーには何も送らない（例外はご意見フォームと、訪問数の計測だけ）。
- JSON の形は README の「データモデル」。単位はセンチメートル。

## 10. 気をつけること・残っている課題

- **2026-10-10 の選択操作**: `main.ts` の `multiSelection` は保存しない一時的な集合で、既存の `selectedId` を主選択として残す。Ctrl/Cmd＋クリックで追加・解除し、2Dは全要素を、3Dは家具をつかんでまとめて動かせる。`selection.ts` が共通の差分を足し、元の座標をスナップし直さない。固定した物は除外する。1ジェスチャー1履歴、Esc・pointercancel・フォーカス喪失で原位置へ戻す。描くツールは短いクリック、置くツールは450msの長押しで選択する。`tests/selection-editor.mjs` は通常のE2Eから呼ぶ。
- **2026-10-10 の和風家具12種類**: 畳・座布団・ちゃぶ台・屏風・障子の衝立・行灯・階段箪笥・囲炉裏・火鉢・縁台・檜風呂・つくばい。`furniture-shapes.ts` の `japaneseParts` と `JAPANESE_MATERIALS` が2D・3D共通の部品データ。高さ1cm〜30m（ほかの家具の下限10cmはそのまま）。標準・横長・縦長・最小の形と高さは家具の単体テストで確認する。

- **前のメールアドレスが古いコミットに残っている**: サイトと README からは消したが、昔のコミットの中には残っている。履歴の書き換えを提案したが、行っていない。どうするかはユーザーが決める。
- **画像付きフォームの自動入力**: 確かめられていない（上の表）。
- **2Dの絵柄の重さ**: 家具がとても多い間取りでは、ドット・筆・古地図・黒板で動かしたときに少し重いことがある。
